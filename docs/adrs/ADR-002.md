# ADR-002: Módulo de Extração de Dados Estruturados e Chat RAG

## Status

Proposto

## Contexto

O FlowScope expande seu escopo para incluir extração de dados estruturados e não estruturados de qualquer ticker listado na B3 (proventos, informes mensais, documentos relevantes em PDF) e oferecer um assistente conversacional com RAG (Retrieval-Augmented Generation) sobre esses documentos. Isso introduz novos domínios, dependências externas (BeautifulSoup, fastembed, liteLLM, PyPDF2), um VectorStore local e uma interface de chat na GUI.

As funcionalidades são organizadas em 4 changes sequenciais:
1. `structured-earnings` — extração de proventos (type=41)
2. `informe-mensal` — extração de informes mensais (type=40)
3. `documentos-relevantes` — extração de PDFs (GetReportsRelevants)
4. `llm-chat` — VectorStore, embeddings, LLM, chat GUI

## Decisões

### 1. Módulo `domain/structured/` para Entidades de Dados Estruturados

**Decisão:** Agrupar todas as entidades e value objects relacionados a dados estruturados da B3 em `domain/structured/` (substituindo o namespace `fii/` proposto originalmente). O domínio de chat fica em `domain/chat/`.

**Alternativa considerada:** Usar o namespace `domain/fii/`.
**Rejeitada porque:** A extração funciona para qualquer ticker, não apenas FIIs. O namespace `structured/` reflete a natureza dos dados (estruturados vs. não estruturados), não o tipo de ativo.

**Consequências:**
```
domain/
├── structured/
│   ├── entities.py       # Entidade, Provento, DocumentoProvento,
│   │                      # CarteiraAtivo, Carteira, Resultados,
│   │                      # Indicadores, OutrasInformacoes, InformeMensal,
│   │                      # DocumentoRelevante
│   └── value_objects.py  # CNPJ, ISIN, ValorProvento, Percentual
└── chat/
    └── models.py          # ChatMessage, ChatSession, DocumentoIndexavel,
                           # DocumentSource (ABC), DocumentoMeta
```

### 2. Resolução de Ticker Tolerante

**Decisão:** `resolver_ticker()` retorna `None` (não lança exceção) para tickers sem dados na API de fundos da B3. O valor `None` também é cacheado (TTL 30 dias) para evitar requisições repetidas a tickers não-fundos.

**Alternativa considerada:** Lançar exceção para tickers não-fundos.
**Rejeitada porque:** O pipeline é ticker-agnóstico. Tickers como `PETR4` devem ser aceitos; as fontes simplesmente retornam lista vazia. Lançar exceção quebraria o fluxo de múltiplas fontes no `llm-chat`.

**Consequências:** Qualquer ticker pode ser consultado em qualquer fonte. Fontes que não encontram dados retornam vazio graciosamente.

### 3. Protocolos Separados por Domínio na Camada de Aplicação

**Decisão:** Protocolos independentes para cada domínio de extração, mesmo quando compartilham assinaturas (`resolver_ticker`, `listar_documentos`):
- `ProventosRepository` — lida com `DocumentoProvento`
- `InformeMensalRepository` — lida com `InformeMensal`
- `EmbeddingPort` — gera embeddings
- `ChatPort` — consulta LLM

**Alternativa considerada:** Protocolo unificado `B3Repository` com todos os métodos.
**Rejeitada porque:** Violaria o Interface Segregation Principle. Embora `ProventosRepository` e `InformeMensalRepository` compartilhem assinaturas, seus tipos de retorno e responsabilidades são distintos. Separar permite testar e evoluir cada domínio independentemente.

**Consequências:** Duplicação controlada de assinaturas (`resolver_ticker`, `listar_documentos` aparecem em 2 protocolos). A implementação compartilha `B3FundosClient` via composição.

### 4. `B3FundosClient` como Extensão por Composição

**Decisão:** `B3FundosClient` é uma classe independente que recebe `CacheManager` por injeção, interagindo com os endpoints `fundsListedProxy` da B3. Não herda de `B3Client`.

**Alternativa considerada:** Subclasse de `B3Client` ou adição de métodos ao `B3Client` existente.
**Rejeitada porque:** `B3Client` lida com CSV de trades e portfolios; `B3FundosClient` lida com API REST de fundos com endpoints e formatos de resposta diferentes. Composição com `CacheManager` compartilhado é mais limpo que herança.

**Consequências:** Dois clientes B3 independentes (`B3Client` para trades, `B3FundosClient` para fundos), ambos usando o mesmo `CacheManager`. Cada um tem responsabilidade única.

### 5. BeautifulSoup para Parsing de HTML Tabular

**Decisão:** Adicionar `beautifulsoup4` como dependência direta no `pyproject.toml` para parsing de documentos HTML da B3.

**Alternativa considerada:** Regex puro ou `html.parser` da stdlib.
**Rejeitada porque:** O HTML da B3 é complexo (tabelas aninhadas, variações de estrutura entre fundos e períodos). BeautifulSoup é a biblioteca Python canônica para parsing HTML (~300KB), amplamente testada e alinhada à filosofia do projeto de usar dependências externas apenas quando estritamente necessário e apenas as amplamente aceitas.

**Consequências:** ~300KB adicionais no binário. Parsing mais robusto e resiliente a mudanças de layout.

### 6. Parsing de HTML com Estratégias Encadeadas

**Decisão:** Funções puras encadeadas em pipeline para extração de dados de HTML (rótulo → tabela → regex), sem uso do Strategy Pattern (ABC).

**Alternativa considerada:** Strategy Pattern com ABC por estratégia de extração.
**Rejeitada porque:** A complexidade não justifica o padrão. O Strategy Pattern é usado para indicadores (22 strategies com lógica de negócio complexa); para parsing, funções compostas são mais simples e alinhadas ao estilo do projeto.

**Consequências:** Módulo `infrastructure/b3/structured_parser.py` com funções puras: `extrair_por_rotulo()`, `extrair_tabelas()`, `identificar_contexto_tabela()`, `classificar_contexto_tabela()`, `limpar_valor_monetario()`, `converter_data_br_para_iso()`.

### 7. Classificação de Tabelas por Palavra-Chave

**Decisão:** Classificar tabelas HTML do informe mensal por match case-insensitive de substrings no heading: `"carteira"`, `"resultado"`, `"indicador"`, `"outras"`. Fallback: `"geral"`.

**Alternativa considerada:** Classificação por posição (primeira tabela = carteira, segunda = resultados).
**Rejeitada porque:** A ordem das tabelas pode variar entre fundos e versões do layout da B3. Classificação semântica é mais robusta.

**Consequências:** Se um heading não contiver nenhuma palavra-chave, os dados são extraídos como dicionário genérico (contexto `"geral"`) em vez de serem descartados.

### 8. Validação Cruzada como Warning

**Decisão:** Divergências entre totais extraídos e calculados (ex: `carteira.total_ativos` vs soma dos `valor_mercado` dos ativos) são logadas como `logger.warning`, não como exceção.

**Alternativa considerada:** Lançar exceção ou descartar dados divergentes.
**Rejeitada porque:** Pequenas divergências podem ocorrer por arredondamento ou dados parciais. Parar o pipeline por uma divergência de centavos seria excessivo. Ambos os valores (extraído e calculado) são preservados para auditoria.

**Consequências:** O consumidor dos dados decide como tratar divergências. O log permite monitoramento sem interromper o fluxo.

### 9. PyPDF2 para Extração de Texto de PDFs

**Decisão:** Usar PyPDF2 (leve, ~3MB) para extração de texto de PDFs da B3.

**Alternativa considerada:** pdfplumber (mais robusto para tabelas, ~10MB em deps).
**Rejeitada porque:** Para o caso de uso (texto para chunk e embedding), a qualidade de extração do PyPDF2 é suficiente. O embedding captura semântica, não layout de tabela. pdfplumber adicionaria complexidade desnecessária de dependências.

**Consequências:** PDFs baseados em imagem (scaneados) não terão texto extraível — cobertura suficiente pois a maioria dos documentos da B3 é gerada digitalmente.

### 10. Cache Binário para PDFs

**Decisão:** PDFs são cacheados como arquivos binários em `~/.cache/flowscope/pdfs/pdf_{id_documento}.pdf`, sem TTL (documentos históricos não mudam). A listagem de documentos usa `CacheManager.get_or_fetch` com TTL de 1 dia.

**Alternativa considerada:** Re-download sempre ou cache no `CacheManager` como string base64.
**Rejeitada porque:** PDFs são binários e podem ser grandes; armazenar como arquivo é mais eficiente que serializar em JSON. Documentos históricos da B3 são imutáveis — re-download seria desperdício.

**Consequências:** Diretório `pdfs/` pode crescer com o uso; sem política de evicção nesta versão.

### 11. VectorStore em SQLite Puro com Cosine Similarity

**Decisão:** Implementar `VectorStore` usando `sqlite3` da stdlib, com embeddings armazenados como JSON BLOB. Busca top-k por cosine similarity em Python puro (`dot(a,b) / (norm(a) * norm(b))`), sem dependências nativas adicionais.

**Alternativa considerada:** sqlite-vec (índices KNN nativos, wheel nativo), chromadb (~200MB em deps).
**Rejeitada porque:** Para o volume típico (~5k chunks × 384d), cosine O(n) em Python leva ~5-10ms por query. Índices nativos não justificam a dependência adicional. Chroma adicionaria ~200MB ao binário.

**Consequências:** Se o volume de documentos crescer para >50k chunks, a busca pode degradar. Threshold documentado para futura migração para índices nativos.

### 12. Chunker de Texto em Python Puro

**Decisão:** Implementar `chunk_text()` em Python puro, dividindo por parágrafos e juntando parágrafos adjacentes até `chunk_size` (default 1000), com `overlap` (default 200) entre chunks consecutivos.

**Alternativa considerada:** langchain `RecursiveCharacterTextSplitter`.
**Rejeitada porque:** langchain adiciona ~200MB em dependências. O algoritmo de chunking necessário é simples (split + merge com overlap) e não justifica o custo.

**Consequências:** Sem dependência de langchain. Chunker simples mas eficaz para o domínio (documentos em português, parágrafos bem definidos).

### 13. fastembed como Embedding Provider Default

**Decisão:** Usar `fastembed` com modelo `BAAI/bge-small-pt-v1.5` (384 dimensões, otimizado para português) como provider de embeddings local e default. liteLLM embeddings via API como alternativa configurável.

**Alternativa considerada:** sentence-transformers (PyTorch, ~1.5GB).
**Rejeitada porque:** fastembed usa ONNX runtime (~120MB) em vez de PyTorch, é 12x menor, e o modelo BGE-small-pt é leve e otimizado para português. sentence-transformers inviabilizaria o binário.

**Consequências:** ~120MB adicionais no binário com `[llm]` (onnxruntime). Modelo de ~130MB baixado na primeira execução (cache huggingface). Embeddings offline, sem custo de API.

### 14. Chat LLM via liteLLM com Múltiplos Provedores

**Decisão:** Usar `litellm.completion()` como camada de abstração para chat LLM, suportando OpenAI, Claude, Gemini, DeepSeek, Copilot e OpenAI-compatible via configuração.

**Alternativa considerada:** SDKs nativos de cada provedor.
**Rejeitada porque:** liteLLM unifica a interface para todos os provedores (~2MB), trocar de provedor é uma mudança de config, não de código.

**Consequências:** Chat requer API key e internet. Sem suporte a modelos locais para chat (fora do escopo).

### 15. Protocolos Separados para Embedding e Chat

**Decisão:** `EmbeddingPort` e `ChatPort` são protocolos independentes, não um `LLMPort` unificado.

**Alternativa considerada:** Protocolo único `LLMPort` com métodos `embed()` e `chat()`.
**Rejeitada porque:** Embedding e chat têm ciclos de vida diferentes (indexação batch offline vs chat em tempo real), providers diferentes (local vs API), e requisitos de teste distintos. Separar permite evoluir cada um independentemente.

**Consequências:** Dois protocolos, duas factories (`create_embedding_provider`, `create_chat_provider`), configuração independente no `config.json`.

### 16. DocumentSource ABC com Implementações Plugáveis

**Decisão:** `DocumentSource` é uma ABC com 3 implementações concretas (`ProventosSource`, `InformeMensalSource`, `RelevantesSource`). Cada uma encapsula a lógica de obtenção de dados de sua respectiva fonte. O `IndexarDocumentosUseCase` itera sobre uma lista de `DocumentSource`.

**Alternativa considerada:** Um método monolítico `indexar_ticker()` que conhece todas as fontes.
**Rejeitada porque:** Cada fonte tem lógica radicalmente diferente (HTML tabular vs PDF download vs API paginada). A ABC isola cada fonte, permite adicionar novas sem modificar o pipeline, e facilita testes (mock de uma fonte específica).

**Consequências:** Fontes futuras (ex: dados da CVM) são plugadas sem alterar o use case.

### 17. ChatPanel como Widget Parametrizado

**Decisão:** Widget único `ChatPanel(ticker: str | None)` reutilizado nas duas abas de chat. A única diferença comportamental é o filtro `WHERE ticker = ?` na busca do VectorStore.

**Alternativa considerada:** Dois widgets separados para Chat Geral e Chat Ticker.
**Rejeitada porque:** Layout, gerenciamento de mensagens, scroll e copy/paste são idênticos. Duplicar ~300 linhas de tkinter para uma diferença de 1 parâmetro violaria DRY.

**Consequências:** `ChatPanel(ticker=None)` para busca global (Chat Geral), `ChatPanel(ticker="ALZR11")` para busca filtrada (Chat Ticker).

### 18. Sessão de Chat Não Persistente

**Decisão:** Cada aba de chat começa com sessão limpa (`ChatSession` in-memory). Nenhum histórico é persistido entre sessões do FlowScope.

**Alternativa considerada:** Persistir histórico em SQLite ou JSON.
**Rejeitada porque:** Simplifica implementação, evita preocupações com privacidade (API keys, conversas), e alinha-se ao fluxo de uso (consultas pontuais, não conversas contínuas).

**Consequências:** Usuário perde o histórico ao trocar de ticker ou fechar o programa. Copy/paste livre mitiga — usuário pode salvar trechos relevantes externamente.

### 19. Configuração LLM no `config.json` Existente

**Decisão:** Estender `~/.flowscope/config.json` com bloco `llm` contendo sub-blocos `embedding` e `chat`, em vez de arquivo separado.

**Alternativa considerada:** Arquivo dedicado `~/.flowscope/llm_config.json`.
**Rejeitada porque:** O projeto já persiste preferências da GUI nesse arquivo. Centralizar evita múltiplos arquivos de config e simplifica carregamento na inicialização.

**Consequências:** Bloco `llm` é opcional; ausência indica chat não configurado. Compatível com versões anteriores do config.

### 20. Dependências Opcionais `[llm]` com Marcador pytest

**Decisão:** Dependências de IA/ML (`litellm`, `fastembed`, `PyPDF2`) são agrupadas como opcionais em `[project.optional-dependencies]` sob a chave `llm`. Testes que dependem dessas bibliotecas usam `pytest.mark.llm`. CI roda duas matrizes: base (`-m "not llm"`) e completa (`-m "llm"`).

**Alternativa considerada:** Dependências obrigatórias em `dependencies`.
**Rejeitada porque:** O binário base (~45MB) não deve crescer para ~185MB para usuários que não usam chat. A GUI detecta ausência com `try: import` e mostra mensagem amigável com instrução `pip install flowscope[llm]`.

**Consequências:** `pyproject.toml` ganha grupo `[llm]`. README documenta instalação opcional. Testes do domínio e use cases não dependem dessas bibliotecas (usam mocks dos ports).
