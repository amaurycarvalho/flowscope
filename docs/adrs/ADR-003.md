# ADR-003: Quality Gate da RFC-005 em CI reutilizável e Release gated

## Status

Aceito

## Contexto

A RFC-005 definiu um quality gate abrangente (lint, complexidade, duplicação, cobertura mínima de 85%, mutação mínima de 80% e segurança com semgrep) para código gerado por IA, mas ele nunca foi implementado. O workflow de release (`release.yml`) publica binários PyInstaller para 3 plataformas sem nenhuma validação prévia de qualidade — o build acontece às cegas, independentemente do estado do código.

O `ci.yml` existente era um workflow simples com um único job (`lint_and_test`) rodando `make lint test` em Python 3.10, sem qualquer reuso. O Makefile tinha apenas 5 targets básicos.

## Decisões

### 1. ci.yml como workflow reutilizável via `workflow_call`

**Decisão:** Adicionar `workflow_call` ao trigger `on` do `ci.yml`, além de `push` e `pull_request` na `main`. Outros workflows (ex.: `release.yml`) passam a invocá-lo como job via `uses: ./.github/workflows/ci.yml`.

**Alternativa considerada:** Duplicar os passos de qualidade inline no `release.yml`.
**Rejeitada porque:** Duplicaria ~40 linhas de config de CI; alterações no gate precisariam ser replicadas em N lugares. `workflow_call` é o mecanismo canônico do GitHub Actions para reuso.

**Consequências:** O gate é binário (pass/fail) para os consumidores. O `ci.yml` precisa expor outputs/artifacts caso consumidores necessitem — atualmente não é necessário.

### 2. Pipeline em 3 jobs encadeados (lint → test → quality-gate)

**Decisão:** Separar o pipeline em `lint`, `test` e `quality-gate`, com dependências via `needs`, em vez de um job monolítico.

**Alternativa considerada:** Job único com todos os passos sequenciais.
**Rejeitada porque:** Jobs separados permitem: (a) paralelismo na matrix 3.12/3.13; (b) falha rápida — lint falha em ~30s sem esperar testes de ~2min; (c) visibilidade — cada job tem seu próprio log e status no GitHub UI.

**Consequências:** `test` depende de `lint`; `quality-gate` depende de `test`.

### 3. Python 3.12 no lint, 3.12 + 3.13 no test/quality-gate

**Decisão:** Lint roda apenas em 3.12 (o resultado independe da versão). Test e quality-gate rodam em matrix 3.12 e 3.13. O `release.yml` mantém Python 3.10 para o build PyInstaller (estabilidade de binário).

**Alternativa considerada:** Manter Python 3.10 em toda a matrix.
**Rejeitada porque:** O projeto já declara `requires-python = ">=3.10"`; testar nas versões mais recentes garante compatibilidade futura conforme a RFC-005.

### 4. Cache de `.venv` no job quality-gate

**Decisão:** Usar `actions/cache@v4` com key baseada no hash do `pyproject.toml` + Python version, reduzindo o tempo de instalação de ~3min para ~20s.

**Consequências:** O cache precisa ser invalidado quando o `pyproject.toml` muda — a key garante isso.

### 5. Makefile expandido conforme RFC-005, mantendo `build` como PyInstaller

**Decisão:** Implementar todos os targets da RFC-005 (`venv`, `install-quality-tools`, `quality-gate`, `complexity`, `duplication`, `mutation-*`, `security*`). O target `build` permanece como PyInstaller (`pip install -q pyinstaller` + `python -m PyInstaller flowscope.spec`), sem wheel publishing.

**Alternativa considerada:** Criar `build-wheel.yml` e publicar wheels.
**Rejeitada porque:** A realidade do projeto é a distribuição de binário único via PyInstaller. Wheel publishing não é um objetivo.

### 6. Scripts Python como entry points de métricas

**Decisão:** Criar `scripts/quality_gate.py` (orquestrador com relatório consolidado JSON), `scripts/complexity_metrics.py` (implementa Contract 2 do Maintainability Index) e `scripts/check-mutation-score.py` (verifica score de mutação ≥ 80%).

**Consequências:** As métricas ficam reproduzíveis localmente e os thresholds centralizados nos scripts.

### 7. release.yml gated por CI

**Decisão:** Adicionar job `ci` que invoca o workflow reutilizável; os jobs `build` (matrix linux/windows/macos) e `release` declaram `needs: ci` / `needs: build`, respectivamente. Nenhum binário é publicado sem o gate passar.

**Alternativa considerada:** Fazer cada job da matrix de build depender de `ci` (redundante).
**Rejeitada porque:** `needs: ci` no job `build` já garante que todos os 3 builds só rodam após o CI passar.

### 8. Grupos `dev` e `quality` separados no pyproject.toml

**Decisão:** `dev` mantém ferramentas leves para desenvolvimento local (ruff, flake8 + plugins, pytest, pytest-cov, responses). `quality` adiciona as ferramentas pesadas (radon, xenon, lizard, mutmut, semgrep). jscpd é instalado via npm global (não é dependência Python).

**Consequências:** Desenvolvedores que só rodam lint+test localmente não instalam radon/mutmut/semgrep. O CI instala o grupo `quality` completo.

## Alternativas Consideradas

- Job monolítico no CI em vez de 3 jobs encadeados.
- Duplicação inline do gate no `release.yml`.
- Manter Python 3.10 em toda a matrix.
- Criar `build-wheel.yml` com publishing de wheels.
- jscpd via pip.

Todas foram rejeitadas pelos motivos documentados nas decisões acima.

## Consequências

- Todo código mergeado deve passar pelo gate completo (blocking desde o dia 1).
- O `release.yml` herda o resultado do job `ci`; builds de plataforma não executam o quality gate, apenas dependem dele.
- O Makefile e o CI compartilham os mesmos targets — drift é mitigado porque o CI usa `make` diretamente.
- O primeiro run do gate pode exigir correções de complexidade, duplicação, cobertura ou mutação no código existente (parte do trabalho de implementação).
